# T006 — RTX 4050 GPU 验证、性能评估与研究结论

日期：2026-11-24。研究分支：`research/gpu-stage-b`。最终研究结论：**`VALUABLE_GPU_EXTENSION`**。

## 1. Executive conclusion

RTX 4050 对较大规模的公开验证和单机五进程 tally 有实际收益，小规模选举应保留 CPU 路径。n=1024 的完整公开验证，三次进程墙钟中位数为 inline CPU **20.543 s**、Rayon CPU **17.839 s**、CUDA **10.520 s**、adaptive **9.592 s**。adaptive 相对较快的 CPU 基线达到 **1.86× / 46.2%** 时间减少；相对原 inline 为 **2.14× / 53.3%**。全部验收谓词通过。

完整选举 n=1024 的本地 tally 为 CPU **24.363 s**、adaptive **16.953 s**，即 **1.44× / 30.4%**；五 trustee 进程的额外启动全包含墙钟为 **85.908 s → 44.049 s**，即 **1.95× / 48.7%**。这两项大型完整选举比较各只有一次有效配对观察，不能当作三次重复的稳健估计。三次重复的引擎与公开验证实验提供补充证据。

原始 CUDA 内核已经有用。本任务没有修改椭圆曲线算术或 CGY 协议，也没有证据支持把 64-thread block 替代默认 128。实际采用的优化是按需创建 CUDA 上下文、保留小批量 CPU、选择保守的 4096-job 分界。GPU 不参与 Groth16 证明生成、秘密份额计算或 EVM 执行。

这是一项有价值的 GPU 工程扩展。现有结果尚不足以独立支撑一篇具有新密码学结果的论文；后续需要可证明的批验证、具有对照消融的调度机制，或更广泛硬件/多机证据。冻结论文、main、v0.2.0、历史链上与六 VM 结果均未修改。

## 5. GPU optimization

**按需 CUDA 初始化。** 原 adaptive 即使所有 batch 都小于阈值，也先创建 device context。Stage B 用 OnceLock 延后创建，只有达到阈值才创建一次；CUDA 错误仍返回错误，不伪装 CPU 成功。同一 n=8 已录取选举、3 次交替 eager/lazy 消融：完整 tally CLI 墙钟中位数 **1.085360 → 0.603599 s**（1.80× / 44.4%）；被测 initialization 中位数 **0.184693 → 0.052865 s**。它消除了小选举不需要的 CUDA 成本；整体差值还包含驱动、进程和设备状态，不能全部等同于 NVRTC 编译耗时。旧二进制与新二进制哈希均保留。

**Launch geometry。** 同一 65536-job 试验、每配置 5 次：

| block threads | backend median s | range s | Driver API resource occupancy model |
|---|---|---|---|
| 64 | 0.047255 | 0.041319–0.049513 | 6 blocks/SM，384 threads/SM，25.0% |
| 128 | 0.047661 | 0.047496–0.047846 | 3 blocks/SM，384 threads/SM，25.0% |
| 256 | 0.064013 | 0.053329–0.065713 | 1 block/SM，256 threads/SM，16.7% |

64 对 128 的中位差小于 1%，range 重叠；没有采用它。CUDA Driver 对实际 NVRTC/PTX JIT function 返回 **146 registers/thread、2048 local bytes/thread、0 static shared bytes、max 384 threads/block**。`cuOccupancyMaxActiveBlocksPerMultiprocessor` 给出上表资源模型；它不是执行期间的实测 achieved occupancy。T005 的 0 spills 不代表没有 local-memory 访问。

Nsight Compute 因 **ERR_NVGPUCTRPERM** 被拒绝，因此没有宣称获得 stall、带宽、指令吞吐或 achieved occupancy 计数。未更改系统性能计数器权限。[NVIDIA 错误说明](https://developer.nvidia.com/ERR_NVGPUCTRPERM)。已成功用 Nsight Systems CUDA activity trace 采集 40 kernel、120 memcpy、40 memset，按每 size 丢弃 1 warmup、保留 3 次：

## 9. Security analysis

公开/秘密边界的源检查：Job 的输入来自 [sigma jobs](../src/sigma.rs#L51)、[Csz jobs](../src/sigma.rs#L243)、[Engine::verify_batched](../src/tally.rs#L754) 与 [Engine::finish](../src/tally.rs#L613)。包括公开点、Fiat–Shamir responses/challenges、整数 subgroup q、Lagrange 系数和 1/2。`Job::subgroup` 保留整数 q，不能先模 q 化成 0。GPU 中的固定窗口不是 constant-time；仅适用于这些公开标量。

秘密 share、mask sign、rerandomization nonce、模拟分支 randomness、voter witness 均留在 [Trustee::act/produce](../src/tally.rs#L865) 的 CPU 生产路径。公开导出使用明确文件 allowlist；Setup 包含公开 commitment/weight/verification key，而非 TrusteeKey/VoterRecord。没有输出私钥、votes、私密 W、ballot proving key 或 authentication seeds。

**必须限定 T005 的安全措辞。** 不向 GPU 发送秘密，是被动信息流性质；它不自动证明恶意 GPU 不影响在线隐私。GPU 同时承担 subgroup/proof 算术检查；若其谎报，在线 CPU trustee 可能在错误接受之后执行秘密相关动作。事后 CPU replay 无法撤销动作。因此本任务在线 GPU 路径信任 CUDA 算术、driver、host/OS 的完整性；未证明主动恶意加速器模型下 Honest-Cast privacy 不变。T005 §6/§9 中“无新隐私假设”的宽泛措辞，应按此收窄理解。原研究报告和论文安全定理没有被改写。

原始 proof statement、same-sign masking、rerandomization ordering、DLEQ、Fiat–Shamir context、accepted-board binding、terminal adapter 与 5-of-5 release 保持不变。Board 仍为 trusted common-view TCP coordinator；这里 trustee 各读取同一私密目录中的独立文件，没有 OS 强制 secret isolation。历史六 VM 证据未被重标为 GPU 多机测试。

故障采样的**分析式、未实现机制**：固定 M 个已承诺 GPU 输出中有 f 个错误；可信 CPU 事后无放回均匀抽 s 个，且 GPU 无法预知或事后改写样本，则

`P(miss) = C(M-f,s) / C(M,s)`。

独立 Bernoulli 采样率 ρ 时为 `(1−ρ)^f`。M=65536、仅 1 个错误、s=16 时检测率只有 **0.0244%**；没有密码学 soundness 保证。若模型预先保证至少 ε 比例错误，则 P(miss)≤(1−ε)^s；ε=1%、目标 miss≤10^-6 需 s≥1375。若设备可预测采样、适应性作恶或改写 CPU 状态，这些式子不适用。完整 CPU 重算提供本实验的最终参考接受；不应把成功测试或少量抽查提升为新 theorem。

## 10. Scientific interpretation

T005 的 Amdahl 2.2× tally / 4.6× replay 上限来自另一台机器及不同测量边界，是预估情境，不是 RTX 的保证。新 CPU hotspot profile 在 n1024 引擎 tally 中 batch_run+finish 占 **50.9%**，对应理想上限 **2.04×**；engine replay 占 **73.5%**，上限 **3.77×**。实际完整 tally 1.44×、完整 public replay 1.86×（对 batched CPU）低于相应范围；秘密 proof production、解析、canonical conversion、签名、hash 和 CPU 检查成为剩余成本。不能用 8.48× 大 batch scalar 加速替代协议加速。

原 T005 对单 job INT32 工作量和强 CPU 吞吐的模型也只是估计；实测 262144-job backend 为约 1.64 M multiplications/s，CPU 约 0.193 M/s。该差异表明需要实际测量；不据此声称超过硬件理论峰值。大 batch、缓存/重复 point pool 和 subgroup 标量分布是本 benchmark 的具体条件。

既有 GPU 密码学已经研究大规模并行算术。[*cuZK*](https://eprint.iacr.org/2022/1321) 加速 Groth16 proof generation 的 MSM/MUL/NTT 并处理 host-device overlap；本任务计算独立 `[k]P`，不是聚合成一个点的 MSM，也没有加速 prover。[*ZKProphet*](https://arxiv.org/abs/2509.22684) 研究 GPU ZKP 的 INT32 与依赖链等瓶颈；其 prover/NTT 结果不能移作本 CGY verifier 的测量。CGY 是 [原始门协议](https://inria.hal.science/hal-03367930v2/document) 的来源；这里没有和作者原实现做相同硬件的软件竞速。

研究问题 A 得到工程证据：公开/秘密划分使真实 threshold 协议中的大量公开验证可 offload，并可由独立 CPU 复核。问题 B 得到有限证据：固定大小阈值在 DAG 诱导的重尾 batch 上有用，但没有提出或验证新的学习/预测调度算法。问题 C 尚无新密码学结果：当前 proof 编码通过 reconstructed commitments 的 Fiat–Shamir hash 检查，不能直接把相互独立的 hash 相等条件用一个线性关系替代。

后续若改成 commitment-form 随机线性批验，必须在固定 batch 后派生不可预测系数，绑定 poll/board/slot/trustee/上下文，证明所有 OR/same-sign 和 DLEQ 关系的联合 soundness，并解决 cofactor。只乘 cofactor 8 会抹掉 torsion，改变原接受谓词；例如阶 2 residual 的取消概率可为约 1/2，不能套用 prime-order 下约 1/q 的界。必须个别 subgroup 检查或给出等价的正式机制、版本化 transcript、单独的证明和负例。T006 未修改这些语句或 transcript 编码。

## 11. Potential paper

可继续研究的暂定题目：**Public-Data GPU Acceleration for Verifiable Threshold Governance**。

中心问题：在不导出 trustee 秘密的条件下，如何利用 threshold computation DAG 产生的 batch 结构，加速公开验证，并为加速器错误建立明确的完整性边界？

建议三项可检验贡献：

1. 对 public/secret 运算划分及 GPU/driver 信任边界给出精确定义和数据流论证，覆盖在线 trustee 及独立 auditor 两种角色。
2. 建立包含 cold/warm、batch composition、CPU 核数及 GPU contention 的成本模型，提出真正可对照的 adaptive DAG 调度，并在多 GPU / 弱 CPU / 独立主机中验证。
3. 如可完成，设计保持 OR/same-sign 与 cofactor 安全的 CGY proof 批验，给出随机系数 soundness 证明、Fiat–Shamir 组合论证及新的 artifact；这项目前完全属于后续工作。

必要补充实验：所有大规模完整选举≥3 次、更多机器与 GPU、隔离桌面负载、实际 counters、cold/warm/context 消融、真实跨 host GPU trustee、吞吐/能耗和独立 verifier 的完整正确性/故障实验。单纯移植 scalar multiplication 不足以声称新 cryptographic contribution。

投稿方向：偏工程/实验完整的版本可考察 CCF C 的 HPCC / HiPC；具有通用调度、模型和跨平台证据的版本可考察 B 的 Euro-Par / IPDPS。分类依据 [CCF 官方目录](https://www.ccf.org.cn/Academic_Evaluation/ARCH_DCP_SS/zgjsjxhtjgjxshy/)及 [HPCC C 类页](https://www.ccf.org.cn/Academic_Evaluation/ARCH_DCP_SS/zgjsjxhtjgjxshy/cl/2017-03-13/586421.shtml)。目录/具体年度 CFP 仍需投稿时核对；此次访问部分官方页面返回 405，不据此给出截稿或录用概率。这里是研究方向建议，不是适配性或录用保证。
